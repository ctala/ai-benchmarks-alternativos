## Respuesta completa

### `success` no significa que haya pasado algo

En n8n, una ejecución puede terminar en `success` aunque no haya producido ningún efecto útil. El estado indica que la ejecución terminó sin un error no gestionado; no confirma que se procesaran registros, se enviara una notificación o se actualizara un sistema externo.

El caso más común: un nodo entrega cero items. Un filtro descarta todo, una rama de un `IF` no recibe datos o una consulta devuelve resultados vacíos. Los nodos posteriores no se ejecutan, pero tampoco hay una excepción que marque la ejecución como fallida. Desde n8n, todo salió según lo previsto.

También puede haber un éxito técnico con un fallo funcional: la API respondió, pero rechazó el cambio; el nodo continuó tras un error configurado para no detener el workflow; o se procesó un conjunto distinto del esperado.

La solución es definir qué significa «hecho» para cada workflow y comprobarlo explícitamente:

- Valida el número de items antes de una operación crítica. Si esperabas al menos uno y no hay ninguno, usa `Stop And Error`.
- Comprueba la respuesta del sistema destino: código, estado y, cuando sea posible, el ID del objeto creado o actualizado.
- Registra un resultado de negocio, no solo el estado de ejecución: `items_received`, `items_processed`, `items_failed` y la acción realizada.
- Añade alertas para resultados anómalos —por ejemplo, cero procesados— aunque la ejecución figure como exitosa.

La pregunta útil no es «¿terminó el workflow?», sino «¿se cumplió la postcondición que esperaba?». Si no puedes responderla mirando los datos de salida o un registro verificable, tu `success` está contando demasiado poco.
