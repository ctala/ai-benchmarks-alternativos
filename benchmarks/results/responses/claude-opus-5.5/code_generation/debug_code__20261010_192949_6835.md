# Análisis de bugs en `process_orders`

## Bug 1: División por cero

```python
average = total / len(processed)
```

**Problema:** Si ninguna orden tiene `status == 'pending'` (o si `orders` está vacía), `processed` queda vacía y `len(processed)` es `0`. Esto lanza `ZeroDivisionError` y la función se cae.

**Ejemplo que falla:**
```python
process_orders([])                                          # ZeroDivisionError
process_orders([{'status': 'shipped', 'total': 50}])        # ZeroDivisionError
```

**Solución:** Verificar antes de dividir.
```python
average = total / len(processed) if processed else 0
```

## Bug 2: Mutación de los diccionarios originales

```python
order['final_price'] = final_price
order['status'] = 'processed'
```

**Problema:** En Python los diccionarios se pasan por referencia. La función modifica los objetos que recibió, y eso causa varios efectos secundarios:

- El llamador ve sus datos alterados sin esperarlo.
- Si llamas a la función dos veces con la misma lista, la segunda vez no procesa nada, porque todas las órdenes ya figuran como `'processed'`.
- Los objetos en `processed` son los mismos que en `orders`, así que modificar uno afecta al otro.

**Ejemplo:**
```python
orders = [{'status': 'pending', 'total': 200}]
process_orders(orders)
print(orders)  # [{'status': 'processed', 'total': 200, 'final_price': 180.0}]  ← ¡modificado!
process_orders(orders)['count']  # 0 en la segunda llamada
```

**Solución:** Trabajar sobre una copia.
```python
processed_order = {**order, 'final_price': final_price, 'status': 'processed'}
```

> Nota: `{**order}` o `dict(order)` hacen una copia *superficial*. Si las órdenes tuvieran estructuras anidadas que se modifiquen (por ejemplo, una lista de items), habría que usar `copy.deepcopy`.

## Bug 3: `count` cuenta las órdenes equivocadas

```python
'count': len(orders)
```

**Problema:** Devuelve el total de órdenes recibidas, no las procesadas. Esto es inconsistente con `total` y `average`, que solo consideran las procesadas. Con 10 órdenes de las que solo 2 son pending, `count` diría 10 y el promedio estaría calculado sobre 2.

**Solución:**
```python
'count': len(processed)
```

## Problemas adicionales (no listados, pero vale la pena considerar)

**4. `KeyError` con datos incompletos.** Si alguna orden no tiene la clave `'status'` o `'total'`, `order['status']` lanza una excepción. Usar `.get()` es más robusto.

**5. Uso de `float` para dinero.** Los floats tienen errores de precisión (`0.1 + 0.2 != 0.3`). Para cálculos monetarios conviene usar `Decimal`, o al menos redondear a 2 decimales.

**6. Número mágico.** El `0.1` y el `100` están hardcodeados. Convertirlos en constantes o parámetros hace el código más claro y configurable.

```python
from decimal import Decimal, ROUND_HALF_UP

DISCOUNT_RATE = Decimal('0.10')
DISCOUNT_THRESHOLD = Decimal('100')
CENTS = Decimal('0.01')


def process_orders(orders):
    """
    Procesa las órdenes pendientes aplicando un descuento del 10%
    a las que superan 100. No modifica la lista ni los diccionarios originales.
    """
    total = Decimal('0')
    processed = []

    for order in orders:
        if order.get('status') != 'pending':
            continue

        order_total = Decimal(str(order.get('total', 0)))
        discount = order_total * DISCOUNT_RATE if order_total > DISCOUNT_THRESHOLD else Decimal('0')
        final_price = (order_total - discount).quantize(CENTS, rounding=ROUND_HALF_UP)

        # Bug 2 corregido: se crea un nuevo diccionario en vez de mutar el original
        processed_order = {
            **order,
            'final_price': final_price,
            'status': 'processed',
        }

        total += final_price
        processed.append(processed_order)

    # Bug 1 corregido: se evita la división por cero
    average = (total / len(processed)).quantize(CENTS, rounding=ROUND_HALF_UP) if processed else Decimal('0')

    return {
        'processed': processed,
        'total': total,
        'average': average,
        'count': len(processed),  # Bug 3 corregido
    }
```
