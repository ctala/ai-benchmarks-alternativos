## Respuesta completa

Un workflow en n8n puede terminar en success y no haber hecho nada porque el motor distingue ejecución técnica de efecto de negocio. Si el trigger recibe un evento válido, el flujo se ejecuta sin errores y ningún nodo lanza excepción, el estado será success. Pero si un IF deja todos los items en false, un Switch no encuentra coincidencia, un Filter vacía el array, una expresión devuelve undefined o un Execute Workflow consume un subflujo que retorna [], el resultado práctico es cero writes, cero llamadas, cero colas. También pasa con Respond to Webhook mal colocado: devuelves 200 antes del nodo crítico, o el nodo queda fuera de la rama que persiste.

La forma de detectarlo no es mirar el status, sino el delta. Primero, instrumenta contadores: cuántos items entraron, cuántos pasaron por cada rama, cuántos writes se confirmaron. Un nodo Function o Code puede emitir métricas o logs estructurados con run_id, workflow_id y etapa. Segundo, usa assertions: si después de transformar esperas N items o un ID, falla cuando no exista. Tercero, activa Error Workflow y alertas no solo por error, sino por ejecuciones success con output vacío o duración anómala. Cuarto, consulta Execution Data vía API o base de datos para comparar success vs items procesados vs efectos externos. Y en flujos asíncronos, exige correlation_id y un heartbeat: si el evento entró pero no hay confirmación en X minutos, dispara reconciliación.

En producción, success significa 'no se cayó'; tu trabajo es convertirlo en 'hizo lo que debía'.
