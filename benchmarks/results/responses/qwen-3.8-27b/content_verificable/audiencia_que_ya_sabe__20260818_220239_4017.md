## Respuesta completa



Un 200 OK no significa que el trabajo se hizo. En n8n, 'success' significa que el workflow terminó sin lanzar una excepción, no que el efecto esperado ocurrió. Eso pasa más de lo que parece: un webhook que valida payload pero no persiste; un cron que dispara pero no encuentra registros; una API que devuelve 200 con empty array; un nodo que salta por condiciones y deja el flujo vacío; un batch procesado con zero items.

El problema no es solo el estado HTTP. Es la diferencia entre ejecución exitosa y resultado verificado. Un workflow puede completar todos sus nodos y, aun así, no crear nada, no enviar nada, no actualizar nada.

Para detectarlo, deja de confiar en 'success' y empieza a medir efectos. Añade una comprobación posterior: consulta el recurso creado, verifica el cambio en la base, cuenta los items procesados, valida el id devuelto o busca un log específico. Si esperabas N filas y llegan 0, falla aunque el workflow termine.

También monitoriza: métricas de items por ejecución, errores por nodo, latencia y resultados vacíos. Alerta cuando un workflow ejecutado por cron o webhook no produce el artefacto esperado. Y añade un nodo de verificación que compare el estado anterior con el posterior.

La regla es simple: success es necesario, no suficiente. Define qué significa éxito para cada workflow y haz que el sistema lo compruebe. Si el efecto no se puede comprobar, el workflow no está terminado. Añade ese chequeo antes de decir que todo está bien.
