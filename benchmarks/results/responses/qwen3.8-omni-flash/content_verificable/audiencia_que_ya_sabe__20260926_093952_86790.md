## Respuesta completa

Success no significa “hecho”

Un workflow puede terminar en verde y no haber tocado una sola fila. En n8n, success suele significar que la ejecución no lanzó error, no que el resultado de negocio sea correcto. El problema aparece cuando el flujo acepta silenciosamente condiciones vacías.

Casos típicos: un Filter elimina todos los items; un IF manda todo a la rama falsa; un HTTP Request devuelve 200 con body vacío; un Code node retorna `undefined` o un array vacío; un Execute Workflow entrega `[]` y pasa desapercibido; un Loop sobre lista vacía no itera; un Set overwrite borra datos antes de persistir. También pasa con webhooks idempotentes: si ya existe la clave, sale sin procesar y la ejecución lo marca OK.

Cómo detectarlo: trata cada nodo crítico como una aserción. Después de Filter/IF, añade un Compare o Code que falle si `items.length === 0` cuando esperabas N. Registra conteos: recibidos, filtrados, enviados, persistidos. Valida esquema y campos obligatorios antes de llamar APIs externas. Para efectos laterales, usa marcadores: escribe un log, métrica o registro con executionId y expectedOutcome. Compara siempre input vs output en tests sintéticos, no solo “no error”.

Mide también latencia y payloads: un 200 en 12 ms puede indicar caché, validación previa o rama corta. En producción, crea un workflow “canario”: mismos triggers, datos falsos, alertas si no hay efecto real esperado.

Regla rápida: si tu workflow puede hacer cero cosas, debe fallar o emitir señal. Verde sin evidencia es deuda silenciosa. Revisa conteos, no estados.
