## Entrada exacta (lo que recibió el modelo)

**user:**

Necesito lanzar una landing page para un nuevo producto SaaS de gestion de inventario. El lanzamiento es en 4 semanas. El equipo tiene 1 disenador, 2 developers y 1 copywriter. Desglosa el proyecto en fases, tareas, dependencias, responsables y un timeline realista.


## Respuesta completa

Aquí tienes un plan de ejecución realista y agresivo para lanzar una landing page MVP de tu SaaS de gestión de inventario en 4 semanas con ese equipo.

He diseñado este plan bajo una filosofía **MVP de landing**: una página de 5–6 secciones, nada de cambios de scope a mitad de camino, y paralelización máxima entre diseño, copy y desarrollo.

---

## 1. Arquitectura recomendada de la landing (Scope MVP)

Para evitar sobrecargar al equipo, la estructura debe ser:

1. **Hero**: Value proposition + CTA principal (Demo/Registrar)
2. **Beneficios / Features**: 3–4 pilares clave del SaaS
3. **Cómo funciona**: 3 pasos simples (ilustraciones o screenshot del dashboard)
4. **Demo interactiva o Video**: Embed o formulario para acceso
5. **Social Proof / Early Adopters**: Logos o testimoniales (incluso si son beta testers)
6. **Precios**: Tabla simple o "Early Access"
7. **FAQ** + Footer (links legales + newsletter)

## 4. Mapa de dependencias críticas (Critical Path)

```plaintext
[Arquitectura de Info] → [Wireframes] → [UI Kit + Mockups] → [Handoff] → [Develop] → [QA/Deploy]
        ↑                                                                                ↑
[Copy Draft] → [Copy Final] ───────────────────────────────────────────────────────────────┘
```

**Las dependencias más delicadas:**
1. **El Copywriter no puede ser cuello de botella.** El draft debe estar listo el mismo día que los wireframes para no retrasar el mockup final.
2. **Los Devs no esperan al handoff para todo.** El setup técnico (repo, staging, analytics blank) se hace en la Semana 1.
3. **El diseño se congela el viernes de la Semana 2.** Ningún cambio de estructura después de esa fecha.

## 5. Riesgos y mitigación

| Riesgo | Mitigación |
|---|---|
| **Scope creep** (pedir más secciones o animaciones complejas) | Documentar el MVP y rechazar cualquier sección nueva en las weekly. Las animaciones deben ser CSS simple (transiciones, fade-ins). |
| **Retraso del copy** | El copywriter debe entregar headlines para el Hero y CTAs en la Semana 1. El resto puede completarse durante la Semana 2 pero antes del handoff. |
| **Inconsistencia mobile** | El diseñador debe entregar mobile junto a desktop, no después. Los devs no deben "inventar" el responsive. |
| **Forms o integraciones fallan** | Probar el envío de formularios y el webhook/CRM desde staging en la Semana 3, no el día del lanzamiento. |

---

## 6. Recomendaciones de stack para velocidad

Dado que tienes solo 2 semanas de desarrollo puro:

- **Framework:** **Astro** o **Next.js (App Router)** para velocidad y SEO nativo.
- **Estilos:** Tailwind CSS para iterar rápido sin escribir CSS custom masivo.
- **Hosting:** Vercel, Netlify o Cloudflare Pages (deploy continuo desde Git).
- **Forms:** Si no hay backend propio aún, usa **Airtable**, **Tally** o **HubSpot Forms** embebidos para no perder tiempo en lógica de servidor.
